# Territory Wars server (MVP)

Небольшой Go-сервер для пошаговой игры с одновременными действиями по контролю территории. Студенты запускают своих Python/C#/Go ботов и подключаются к серверу учителя через WebSocket.

## Требования

- Go 1.22+
- Сетевой доступ со студенческих машин к серверу

## Запуск

```bash
go mod tidy
go build -o bin/server ./cmd/server/
./bin/server -config config.json
```

Переменные окружения переопределяют значения из config.json:

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `PORT` | `8080` | Порт HTTP |
| `MAX_PLAYERS` | `30` | Максимум зарегистрированных игроков |
| `MAX_TURNS` | `200` | Максимум ходов в игре |

Примечание: `TURN_TIMEOUT_SECONDS` не используется — turn delay настраивается через `turn_delay` в `config.json`.

## Жизненный цикл игры

Игра **не запускается автоматически**. Её нужно запустить явно:

```bash
# Запустить игру
curl -X POST http://localhost:8080/api/v1/start

# Остановить игру (сбрасывает всё)
curl -X POST http://localhost:8080/api/v1/stop
```

Или через **интерактивную консоль** (работает на stdin):

```
Команды: start, stop, pause, resume, results, quit
```

## Регистрация игрока

```bash
curl -X POST http://localhost:8080/api/v1/join \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice"}'
```

В ответе содержатся `player_id`, `token` и `websocket_url`. Храните токен в секрете.

Подключение:

```text
ws://localhost:8080/ws?token=YOUR_TOKEN
```

Сервер отправляет `CONNECTED`, затем одно `OBSERVATION` для текущего хода. Отправьте одно действие за ход:

```json
{
  "type": "ACTION",
  "turn": 0,
  "actions": [
    {"type": "expand", "target": {"x": 20, "y": 4}}
  ]
}
```

После отправки действия сервер отвечает `ACTION_ACCEPTED`. Когда раунд разрешается, всем подключённым клиентам отправляется `TURN_RESOLVED` (включая результаты раунда),
за которым следует ровно одно `OBSERVATION` для следующего хода. Пропущенное действие становится `pass` по таймауту раунда. Переподключающиеся клиенты получают текущее наблюдение.

Поддерживаемые действия:

- `expand`: захватить соседнюю нейтральную клетку, стоит 1 энергию
- `attack`: нанести урон соседней вражеской клетке, стоит 2 энергии
- `fortify`: добавить 2 здоровья одной из ваших клеток, стоит 2 энергии
- `pass`: ничего не делать

## HTTP-эндпоинты

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/health` | Проверка здоровья |
| `POST` | `/api/v1/join` | Регистрация игрока (`{"name":"..."}`) |
| `GET` | `/api/v1/state` | Получить текущее наблюдение (`Authorization: Bearer TOKEN`) |
| `GET` | `/api/v1/leaderboard` | Получить таблицу лидеров и статус игры |
| `GET` | `/api/v1/results` | Получить финальные результаты (после окончания игры) |
| `POST` | `/api/v1/start` | Запустить игру (без тела) |
| `POST` | `/api/v1/stop` | Остановить игру, сбросить состояние, отключить всех клиентов |
| `POST` | `/api/v1/pause` | Поставить игру на паузу (остановить обработку ходов) |
| `POST` | `/api/v1/resume` | Продолжить игру (возобновить обработку ходов) |

## Viewer

Реалтайм-вьюер карты доступен по адресу:

```
http://localhost:8080/viewer
```

Он использует Server-Sent Events (SSE) на `/api/v1/viewer/events` для потоковой передачи обновлений состояния игры.

## Правила игры в этом прототипе

- Карта: 40 × 40, тороидальная (координаты wrap-around)
- 30 позиций спавна (до max_players)
- Каждый игрок начинает с 5 энергии и базы
- Одно действие на игрока за ход
- Все отправленные действия разрешаются одновременно в границе раунда
- Пропущенное действие становится `pass` по таймауту хода
- Матч заканчивается после `MAX_TURNS`

## Боты

Сервер автоматически создаёт ботов при `bots_enabled: true` в `config.json`. Боты создаются с ротацией стратегий и уникальными seed (base=42).

```json
{
  "port": 8080,
  "max_players": 30,
  "max_turns": 200,
  "width": 40,
  "height": 40,
  "turn_delay": "1s",
  "bots_enabled": true
}
```

Поддерживаемые стратегии ботов: `simple`, `aggressive`, `defensive`, `expansion`, `random`.

## Архитектура

### Round Manager

Одиночный экземпляр `RoundManager` координирует все раунды. Это единственный мост между
WebSocket-хендлерами и игровым движком.

```
WebSocket handler ──► SubmitAction(actionCh) ──► run() event loop
                                                         │
                                           engine.Submit()
                                           engine.TurnSignal()
                                                         │
                                           enqueue(TURN_RESOLVED)
                                           enqueue(OBSERVATION)
                                                         ▼
                                               all connected clients
```

**Архитектура event-loop:** Один горутин `run()` сериализует всю обработку действий и
разрешение раундов. У каждого игрока есть per-player action channel; WS-хендлер пишет
действия в этот channel вместо прямого вызова движка. Это предотвращает data races
и устраняет баги двойного разрешения.

### Жизненный цикл событий

Каждый ход следует строгому порядку:

1. **ACTION_ACCEPTED** — отправляется игроку, который отправил, сразу после принятия.
2. **TURN_RESOLVED** — транслируется всем подключённым клиентам, когда все игроки отправили
   (или таймаут истёк). Включает per-player результаты.
3. **OBSERVATION** — отправляется каждому клиенту после TURN_RESOLVED, показывая состояние доски для
   следующего хода.

Инвариант `ACTION_ACCEPTED → TURN_RESOLVED → OBSERVATION` гарантирован single-threaded event loop.

### Безопасность переподключения

У каждого подключения игрока есть монотонно увеличивающийся счётчик `generation`. Когда игрок переподключается:

1. Старое подключение помечается текущим generation.
2. Новое подключение получает `generation + 1`.
3. Event loop валидирует generation перед обработкой действий от подключения.
4. Устаревшие действия от старого подключения тихо отбрасываются.

Это предотвращает отправку действий переподключающимся игроком, которые уже были обработаны
их предыдущим подключением.

### Ограниченные outbound-очереди

У каждого игрока есть bounded outbound channel (ёмкость 256). Если очередь заполняется (клиент медленно потребляет события),
подключение корректно отключается. Клиент может переподключиться и получить текущее наблюдение.

### Graceful shutdown

Сервер игнорирует `SIGINT` и `SIGTERM`, чтобы пережить убийство группы процессов harness.

## Тестирование

Запустите все тесты с race detector:

```bash
go test -race -v ./...
```

Категории тестов:

| Пакет | Тесты |
|-------|-------|
| `internal/game` | Юнит-тесты движка — join, authenticate, submit, resolve, timeout, observation, leaderboard, game-over |
| `internal/server` | Тесты Round Manager — connect, disconnect, generation tracking, action submission, event ordering, shutdown, bounded queues, concurrent submits |
| `internal/server` | Интеграционные тесты — реальные WebSocket-клиенты через `httptest.Server`, action flow, timeout resolution, reconnect, event ordering |

## Известные ограничения MVP

Это стартовая реализация, не продакшн экзамен-система:

1. Регистрация всё ещё открыта и возвращает токены публично. Для экзамена предварительно создайте roster или защитите регистрацию admin-ключом.
2. `CheckOrigin` и CORS перmissive для локальной разработки. Ограничьте разрешённые origins перед экспозицией сервера.
3. Нет persistence, TLS termination, rate limiting, replay storage или admin authentication пока.
4. Текущее наблюдение карты раскрывает все клетки. Добавьте fog-of-war filtering, если скрытая информация часть игры.
5. Этот первый ruleset намеренно маленький. Баланс и scoring нуждаются в playtesting.
6. Round coordinator использует bounded outbound queue per connected client. Клиент, который перестаёт потреблять события, отключается; он может переподключиться и получить текущее наблюдение.

Слой координации WebSocket теперь централизован: хендлеры больше не опрашивают движок или независимо отправляют наблюдения. Движок сигнализирует о переходах раундов, и менеджер транслирует `TURN_RESOLVED` плюс одно next-turn observation каждому подключённому клиенту.
