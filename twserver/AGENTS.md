# Territory Wars — Правила серверной части

## 1. Назначение

Каталог содержит серверную часть Territory Wars.

Основные компоненты:
- игровой движок;
- модели игрового состояния;
- правила игры;
- RoundManager;
- REST API;
- встроенные игровые боты;
- HTTP-визуализация;
- управление матчами.

Сервер является авторитетным источником игрового состояния.

## 2. Главный архитектурный принцип

Все игровые изменения выполняются исключительно игровым движком.

RoundManager управляет жизненным циклом ходов.

REST API, встроенные боты и другие компоненты не должны реализовывать собственную логику изменения игрового состояния.

Не создавать параллельные игровые циклы.

## 3. Игровой движок

Игровой движок (`twserver/internal/game/engine.go`) отвечает за:
- состояние карты;
- состояние участников;
- ресурсы;
- игровые объекты;
- валидацию действий;
- выполнение действий;
- разрешение конфликтов;
- обновление состояния;
- определение завершения матча;
- расчёт результатов.

**Правила Engine:**

1. Все поля защищены `sync.RWMutex`.
2. `Token` — 48-символьный hex (randomHex(24) → crypto/rand).
3. `tokenToPlayer` map связывает токен с playerID.
4. `pending` map — действия, ожидающие разрешения.
5. `gameOver` и `stopped` флаги управляют жизненным циклом.
6. `turnChanged` channel пересоздаётся после каждого разрешения хода.

Правила игры должны находиться в одном месте.

При изменении игровых правил:
- обновить соответствующие тесты;
- проверить влияние на все стратегии;
- проверить API;
- обновить документацию.

Не дублировать правила в REST-обработчиках или встроенных ботах.

## 4. RoundManager

RoundManager (`twserver/internal/server/round_manager.go`) является центральным координатором игровых ходов.

Он отвечает за:
- начало нового хода;
- формирование Observation;
- сбор действий;
- проверку поступивших действий;
- обработку таймаутов;
- разрешение хода;
- переход к следующему ходу;
- завершение матча.

Все типы участников должны использовать единый RoundManager.

**Правила RoundManager:**

1. Один `run()` goroutine — единственный обработчик действий.
2. Per-player action channels (`actionCh`) — WS-хендлер пишет в канал, `run()` читает.
3. Generation counter — предотвращает обработку действий от старых соединений.
4. Bounded outbound queue (capacity 256) — переполнение → disconnect.
5. `cleanupAll()` — закрывает все WS-соединения при `StopGame`.

Не допускать:
- двойной обработки одного действия;
- повторного завершения одного хода;
- блокировки игрового цикла;
- конкурентного изменения состояния;
- обработки действий из устаревшего хода.

Для каждого действия необходимо учитывать идентификатор участника и номер хода.

## 5. Внешние участники

Внешние участники подключаются через REST API (`twserver/internal/server/server.go`).

REST API должен:
- регистрировать игроков;
- предоставлять Observation;
- принимать Action;
- проверять идентификаторы и принадлежность действий участнику;
- обрабатывать ошибки;
- соблюдать таймауты;
- возвращать предсказуемые HTTP-ответы.

**Правила HTTP:**

1. Все POST-эндпоинты проверяют `r.Method != http.MethodPost`.
2. `writeJSON()` — единая функция для JSON-ответов.
3. `bearer(r)` — извлечение токена из `Authorization` header.
4. `http.MaxBytesReader(w, r.Body, 4096)` — ограничение размера тела запроса.
5. `signal.Ignore(syscall.SIGINT, syscall.SIGTERM)` — сервер игнорирует сигналы для выживания при kill harness.
6. CORS `Access-Control-Allow-Origin: *` — только для локальной разработки.

HTTP-обработчики не должны содержать игровые правила.

Они должны преобразовывать HTTP-запросы в вызовы существующих внутренних интерфейсов.

## 6. Встроенные боты

Встроенные боты (`twserver/internal/server/bot.go`) работают внутри процесса сервера.

Они не используют HTTP API для общения с игровым движком.

Предусмотрен единый внутренний интерфейс принятия решений:

```go
type PlayerAgent interface {
    Decide(ctx context.Context, observation *game.Observation) (game.Action, error)
}
```

### 6.1 Требования

- Боты получают только собственные Observation.
- Боты не имеют прямого доступа к полному игровому состоянию через стратегию.
- Боты передают действия через RoundManager.
- Боты используют общую серверную валидацию.
- Для каждого бота предусмотрен собственный экземпляр стратегии.
- Для принятия решения установлен таймаут.
- Ошибка одного бота не должна останавливать весь матч.
- Все действия должны быть привязаны к конкретному игроку и ходу.

### 6.2 Стратегии

Поддерживать расширяемую систему стратегий.

Начальный набор:
- RandomBot;
- AggressiveBot;
- DefensiveBot;
- ExpansionBot.

Стратегии должны быть независимы от механизма регистрации игроков и разрешения ходов.

Случайные генераторы должны иметь независимые seed.

При одинаковом seed и одинаковом Observation стратегия должна давать воспроизводимый результат, если её реализация не использует другие источники случайности.

**Правила ботов:**

1. Боты НЕ запускаются автоматически при старте сервера.
2. Боты запускаются через `StartBotsOnDemand()` при вызове `StartGame()`.
3. `BuildBotList(enabled, maxPlayers)` — создаёт агентов с ротацией стратегий и уникальными seed (base=42).
4. Имена ботов: `Bot-aggressive-1`, `Bot-defensive-2`, `Bot-expansion-3`, `Bot-random-4`, `Bot-simple-5`.
5. Боты реализуют `PlayerAgent`, а не `IGameStrategy`.
6. `StrategySimple` определён в `bot_config.go` но не используется в `BuildBotList`.

## 7. Конкурентность

Go-сервер должен безопасно работать с несколькими одновременно участвующими игроками.

Основные требования:
- исключить data race;
- не допускать конкурентной модификации игрового состояния;
- использовать mutex и другие средства синхронизации обоснованно;
- избегать длительного удержания блокировок;
- корректно завершать горутины;
- использовать context для отмены операций;
- контролировать параллелизм ботов.

Не запускать неограниченное количество горутин без необходимости.

Не выполнять пользовательскую стратегию под блокировкой игрового состояния.

Не допускать ситуации, когда зависшая стратегия блокирует RoundManager.

**Правило:** Обязательно проверять изменения конкурентного кода через:

`go test -race ./...`

## 8. Observation и защита информации

Формирование Observation (`twserver/internal/game/types.go`) должно учитывать права конкретного участника.

Не возвращать полное игровое состояние там, где требуется ограниченное наблюдение.

Встроенные боты должны получать те же логические данные, что и внешние игроки.

Не передавать стратегии ссылки на изменяемые внутренние структуры движка.

Использовать безопасные копии или неизменяемые представления данных, соответствующие архитектуре проекта.

## 9. HTTP-визуализация

HTTP-визуализация (`twserver/internal/server/viewer.go`) должна быть read-only.

Она получает отдельное представление состояния игры.

Не предоставлять браузеру прямой доступ к внутренним игровым объектам.

Не блокировать игровой цикл при формировании снимка состояния.

Для событий использовать предусмотренный механизм уведомлений.

При использовании SSE или WebSocket:
- обрабатывать отключения;
- корректно освобождать ресурсы;
- не допускать утечек соединений;
- предусмотреть получение полного состояния после переподключения.

История матчей должна формироваться на основании фактических результатов игровых ходов.

**Правила Viewer:**

1. `viewer.html` встраивается через `//go:embed viewer.html`.
2. SSE использует `EventSource` в браузере.
3. `StartMonitoring(ctx)` — фоновый goroutine, транслирующий обновления каждые 5 секунд.
4. Viewer не требует аутентификации.
5. `buildViewerState()` собирает данные из Engine и BotManager.

## 10. Конфигурация

Конфигурация (`twserver/internal/server/bot_config.go`) должна поддерживать:
- параметры игрового движка;
- параметры HTTP-сервера;
- таймауты;
- максимальное количество участников;
- включение и отключение ботов;
- количество ботов;
- индивидуальные стратегии;
- случайные seed;
- параметры визуализации.

Не зашивать изменяемые параметры в исходный код.

Проверять конфигурацию при запуске.

При некорректных параметрах возвращать понятную ошибку.

## 11. API и обратная совместимость

Не менять существующие HTTP-маршруты и JSON-контракты без необходимости.

При изменении API:
1. Обновить спецификацию (`docs/api-spec.md`).
2. Оценить обратную совместимость.
3. Обновить тесты.
4. Проверить Python, C# и Go клиенты.
5. Обновить документацию.

Не использовать внутренние структуры движка непосредственно в публичных JSON-ответах.

Предпочирать отдельные DTO.

## 12. Логирование и диагностика

Логировать:
- начало и завершение матча;
- регистрацию участников;
- начало и завершение ходов;
- получение действий;
- ошибки участников;
- ошибки встроенных ботов;
- таймауты;
- системные ошибки.

Использовать структурированное логирование.

Логи должны позволять восстановить последовательность событий матча.

Не выводить секреты и чувствительные данные.

**Правило:** Все логи сервера идут через `log.Printf` / `log.Fatalf`. Не используйте `fmt.Println` для логов.

## 13. Тестирование

Обязательные направления тестирования:

### Игровой движок
- все типы действий;
- валидация;
- ресурсы;
- конфликты;
- граничные условия;
- завершение матча.

### RoundManager
- сбор действий;
- таймауты;
- повторная отправка;
- отключение игроков;
- синхронизация;
- переходы между ходами.

### Встроенные боты
- регистрация;
- получение Observation;
- принятие решений;
- таймауты;
- ошибочные действия;
- смешанные матчи.

### HTTP API
- регистрация;
- получение наблюдений;
- отправка действий;
- обработка ошибок;
- совместимость JSON.

### Визуализация
- сериализация состояния;
- обновления;
- история;
- отключения и переподключения.

### Конкурентность
- `go test -race ./...`;
- параллельное выполнение стратегий;
- отсутствие deadlock;
- корректное завершение горутин.

**Правила тестирования:**

1. Все тесты должны проходить с `-race`.
2. Интеграционные тесты используют `httptest.Server` — без реального HTTP-сервера.
3. Тесты RoundManager не используют реальные WS-соединения (conn=nil).
4. Тесты ботов проверяют все стратегии и edge cases.
5. Тесты конфигурации проверяют defaults, overrides, invalid input, path resolution.

## 14. Производительность

Целевая нагрузка — не менее 20 одновременно участвующих игроков.

При оптимизации:
- не создавать ненужные копии состояния;
- не сериализовать игровое состояние без необходимости;
- не блокировать движок HTTP-запросами;
- ограничивать параллелизм;
- избегать преждевременной оптимизации без измерений.

Корректность важнее микрооптимизаций.

## 15. Жизненный цикл игры

**Правила жизненного цикла:**

1. Игра НЕ начинается автоматически.
2. `StartGame()` запускает ботов для заполнения оставшихся слотов.
3. `StopGame()` сбрасывает ВСЁ: токены, соединения, состояние, ботов.
4. После `StopGame` клиенты должны заново пройти `Join` для получения нового токена.
5. `gameOverHandler` — после окончания игры сервер ждёт Enter для остановки.

## 16. Известные ограничения MVP

1. Регистрация открыта и возвращает токены публично. Для экзамена — предсоздать список или защитить admin key.
2. `CheckOrigin` и CORS пермиссивны для локальной разработки.
3. Нет persistence, TLS, rate limiting, replay storage, admin authentication.
4. Наблюдение раскрывает все клетки. Добавить fog-of-war при необходимости.
5. Текущий ruleset намеренно мал. Нужен playtesting для баланса.
6. Round coordinator использует bounded outbound queue. Клиент, который не потребляет события, disconnects.

## 17. Завершение работы

После изменений:
- выполнить gofmt;
- запустить unit-тесты;
- запустить интеграционные тесты;
- выполнить `go test -race ./...` при изменении конкурентного кода;
- проверить сборку;
- проверить запуск сервера;
- обновить документацию.

В итоговом отчёте указать:
- изменённые компоненты;
- принятые архитектурные решения;
- результаты тестирования;
- результаты проверки конкурентности;
- оставшиеся ограничения.
