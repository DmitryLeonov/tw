# AGENTS.md — Territory Wars

## 1. Назначение проекта

Territory Wars — экзаменационная платформа для проверки навыков разработки игровых алгоритмов.

Платформа позволяет студентам писать автономных игровых ботов на различных языках программирования и подключать их к централизованному игровому серверу.

Основные компоненты:
- игровой движок на Go;
- RoundManager для управления ходами;
- REST API для внешних участников;
- встроенные боты;
- HTTP-визуализация игрового поля;
- эталонные клиенты на Python, C# и Go.

Главная задача разработки — поддерживать единую, предсказуемую и расширяемую архитектуру.

## 3. Архитектурные принципы

### 3.1. Сервер — единственный источник истины

Игровой сервер является авторитетным источником состояния игры.

Только сервер:
- изменяет игровое состояние;
- проверяет допустимость действий;
- рассчитывает результаты действий;
- разрешает конфликты;
- начисляет и списывает ресурсы;
- определяет победителей;
- завершает матч.

Клиенты и визуализация не должны самостоятельно изменять игровое состояние.

### 3.2. Разделение компонентов

Не смешивать:
- игровые правила;
- управление игровыми ходами;
- сетевое взаимодействие;
- стратегии ботов;
- визуализацию;
- конфигурацию;
- журналирование.

Изменение одного компонента не должно требовать ненужной переработки остальных.

### 3.3. Единая игровая логика

Все участники матча должны использовать один игровой движок и один механизм разрешения ходов.

Запрещено:
- создавать отдельный игровой цикл для встроенных ботов;
- реализовывать отдельную обработку атак для разных типов игроков;
- обходить существующую валидацию действий;
- предоставлять отдельные правила начисления ресурсов.

## 4. Игровой протокол

### 4.1. Единый контракт

Все внешние клиенты должны работать с одним REST API.

Фактический контракт определяется реализацией сервера и его актуальной документацией.

При изменении протокола необходимо:
1. Обновить спецификацию API.
2. Проверить обратную совместимость.
3. Обновить затронутые клиенты.
4. Обновить интеграционные тесты.

### 4.2. Observation

Observation содержит только ту информацию, которую разрешено видеть конкретному участнику.

Запрещено:
- передавать клиентам внутреннее состояние движка;
- раскрывать скрытую информацию;
- предоставлять внешним участникам данные, недоступные другим игрокам;
- использовать внутренние структуры сервера как публичные модели API.

Все стратегии, включая встроенные боты, должны работать на одинаковом уровне доступной информации.

### 4.3. Action

Все действия участников проходят серверную валидацию.

Нельзя полагаться на то, что клиент корректно проверил ресурсы, координаты или допустимость цели.

Ошибочные действия должны обрабатываться существующим механизмом движка.

## 5. Синхронизация и конкурентность

- RoundManager является центральным координатором ходов.
- Нельзя изменять состояние игры в обход предусмотренного механизма синхронизации.
- Не допускать конкурентной модификации игровых структур.
- Длительные операции не должны блокировать игровой цикл.
- Все горутины должны иметь определённый жизненный цикл.
- Контексты и отмена операций должны обрабатываться корректно.
- Учитывать возможные deadlock, race condition и утечки ресурсов.

Для Go-сервера обязательно использовать `go test -race ./...` после изменений, затрагивающих конкурентность.

## 6. Встроенные боты

Встроенные боты работают непосредственно внутри серверного процесса.

Они:
- не используют REST API для взаимодействия с собственным сервером;
- не создают HTTP-запросы для передачи действий;
- используют внутренний контракт принятия решений;
- получают Observation;
- передают Action через предусмотренный механизм RoundManager.

Внешние клиенты используют HTTP API.

Оба типа участников используют один движок, одну валидацию и один механизм разрешения ходов.

## 7. Визуализация

Веб-интерфейс является наблюдателем игрового процесса.

Он:
- получает состояние через отдельный read-only интерфейс;
- не изменяет игровые данные;
- не блокирует игровой цикл;
- не получает доступ к внутренним структурам без необходимости;
- корректно обрабатывает переподключения и устаревшие данные.

Визуализация должна отражать фактическое состояние движка, а не самостоятельно рассчитывать игровые результаты.

## 8. Безопасность

- Не доверять данным от внешних клиентов.
- Проверять все входные параметры.
- Ограничивать размеры входящих запросов.
- Использовать таймауты сетевых операций.
- Не раскрывать внутренние ошибки и секреты в HTTP-ответах.
- Не записывать токены и секреты в логи.
- Не предоставлять браузерному интерфейсу возможности изменения состояния игры без отдельного обоснованного требования.
